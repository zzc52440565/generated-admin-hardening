# 逐菜单、逐页面的业务改造与循环复验

完整加固的必读协议。不能把“能打开、CRUD能用、共享CSS已换”当成业务适配。仅审查或仅更新图表时遵守用户限定的范围。

## 1. 先按业务设计目标页面，再由脚本固定任务

必读并执行 [页面任务合同](page-task-contract.md)。唯一调度单位是角色×目标菜单×业务页面；页面内所有业务、主从明细、按钮、权限、接口、状态、异常、返工和复测均归原任务，不再让模型临时逐按钮规划。

先对照独立业务事实与当前实现编写 `docs/page-business-plan.json`，使用随包 `page_tasks.py scan/compile`生成 `docs/page-task-plan.json`，队列存项目外检查点。目标导航、页面和布局须由角色职责及业务流程决定，不能将脚手架菜单直接锁死。默认脚本反查不能覆盖的入口须显式核对，源码观察不是业务预期。

### 审计覆盖与任务边界

同时读取静态/动态菜单、路由、权限、前端页面和接口，从每个真实角色的菜单逐层核对，建立 `docs/page-redesign-audit.json`。无菜单入口的登录、首页、深链接、创建、编辑、详情、子路由、弹窗和业务步骤也纳入；同一URL在不同角色下能力不同则分别登记。弹窗/步骤可用 `/orders#edit` 等可定位入口，不必为了登记新增路由。纯目录菜单记录其所有后代页面，操作按钮记录在所在页面。详情、弹窗和步骤可保留独立审计条目，但通过auditPageIds归属同一个业务页面任务，不另派任务。

每页记录角色、入口、所属菜单、源码及调用依据、当前页面形态、用户目标、业务对象、主要动作和适用状态。复用组件可以共享实现与证据，但不能省略独立页面/角色的业务判断。没有菜单的应用允许菜单清单为空，仍需核对全部真实入口。

页面数量必须来自代码和真实界面双重核对；静态定义含已禁用/废弃入口时记录排除依据，不因无权限测试、空数据或打不开而漏登。先目标页面合同与源码对账后改造，最终再重新枚举一次，新增/归并/移除入口同步清单与授权引用。

## 2. 每页先回答业务问句，再决定页面形态

- 谁在什么场景完成什么目标？完成后业务状态、数据或下一步应怎样变化？
- 单条记录是否可以独立维护？是否需同时处理主从明细、上下文、状态或前置条件？
- 用户主要在查找/批量维护记录，还是按时间、资源、阶段、会话或连续步骤办理业务？
- 现有通用列表＋编辑弹窗能否自然完成这项任务，是否迫使用户跨菜单拼数据或手工维持业务一致性？

每页选一个结论并给出具体证据，不能写“按业务优化”作为理由：

| 结论 | 何时选择 | 必须落实 |
| --- | --- | --- |
| `optimize-list` 保留并优化列表 | 以独立记录检索/维护为主，列表适配任务 | 优化字段与信息优先级、筛选、主操作、表单/详情、空态、反馈及适用布局；保留合理表格，不强改成卡片 |
| `redesign-business` 业务改造 | 当前是通用/混合CRUD，真实任务有上下文、生命周期或业务流程 | 改成适配的业务工作页，提供必要上下文、真实业务动作及状态反馈，不能仅更换列表外观 |
| `refine-business` 完善已有业务页 | 原来已有专用业务结构 | 保留有效能力，修正信息、交互或流程缺口，逐页说明实际改进 |

**单据型业务必须合并**：订单＋订单明细、采购单＋采购明细、出入库单＋明细这类，必须做成一个业务工作页（表头＋明细＋合计＋状态流转），不能拆成两个独立 CRUD 列表页，也不能用“办理”按钮跳回无上下文的通用编辑弹窗。只有子记录能独立存在、可独立创建、主单失效后仍有独立生命周期时（如 SKU、库存流水、审计记录）才保持独立，并按 [主从单据归并](master-detail-merge.md) 写明理由。登录页首次执行即改造。

下列只是识别信号，不能据此给项目凭空增加功能：单据需表头＋可编辑明细、状态与后端合计；已有审批需待办、上下文和受控流转；预约/排班需时间与资源冲突处理；考试需实际答题和提交反馈；消息需真实会话与未读；报表需明确口径、筛选与可追溯明细。页面仍可包含列表，但不能让通用增删改查代替主要业务操作。

登录页首次执行即改造。每个菜单下的每个页面都要合理改进；适合列表的保留列表做针对性优化。统一设计语言应来自业务的信息层级、导航和操作习惯，不能靠每页换颜色/组件堆叠制造差异。

## 3. 业务改造必须贯通真实实现

对每个业务动作记录“前置状态/角色 → 输入和校验 → 实际调用方法 → 数据/状态结果 → 页面反馈”。导航、查询、下载等也可以是合法主要动作，不强求每页写数据库；纯客户端动作引用真实客户端实现，有后端的动作同时追踪接口、服务和授权，不能仅引用按钮组件。

必要时同步 API、业务服务、权限、状态校验、事务、重复提交控制和查询缓存；复用既有职责。主从一次提交、后端重算、归属检查等按已有业务落实，不能用“办理”按钮跳回无上下文的通用编辑弹窗应付。保留全部有效功能，清理被替代的入口和调用方，避免双轨实现。

遵守保表/字段/技术栈红线。受限而不能完成的页面留 `blocked` 或未验证，说明替代路径；不能标为业务通过。不要为了套示例新增不存在的审批、支付、排班等产品能力。

## 4. 让检查真正形成闭环

1. **判定与实现**：完成逐页判定，按依赖改造共享组件及每个受影响页面、调用方，写好相关测试。此时只能写“已实现，待验收”。必要复现先采基线，最终测试在全部相关实现完成后集中执行。
2. **业务形态复审**：对照原用户目标和完成条件重新审视最终画面，说明为什么该形态能完成任务、原CRUD局限如何消除；不能拿“改了CSS”充当复审证据。
3. **真实操作验收**：按页面和角色实际打开、操作、观察请求/方法返回、业务结果和权限拒绝，检查正常、适用空态/加载/失败/无权/锁定等状态，以及用户指定的目标视口（仅 PC 任务不扩展移动端）。截图、交互结果和尺寸证据单独保留。正常路径成功不能代替失败恢复。
4. **失败回流**：页面记录轮次、代码版本、问题ID和现象，标 `rework`。修复根因及所有受影响共享页面，重新执行该页的业务复审与相关实测，后轮明确关闭旧问题。修改会影响原验收时旧结果失效；未受影响证据可以复用，但须说明文件/依赖未变的依据，不能机械重跑全仓构建。
5. **最终全量核对**：从真实菜单、路由和角色重新枚举，与清单逐项对照；检查全部页面及动作/状态、剩余问题、源码指纹和证据版本。漏页、特殊业务仍是通用CRUD、问题未关闭、只有样式修改、证据缺失/失效、只测一个角色均不得标整项完成。

不要求固定轮数；首次通过可收口，有问题则继续修复与复验。同一失败重复且无进展时先重查根因和方案，不机械无限重试。缺凭据、平台或红线限制时如实记录，继续独立工作，交付时说明未完成与恢复方式。

## 5. 可执行的覆盖与证据检查

字段和完整样例见 [页面审查记录格式](page-redesign-audit-format.md)。完成真实复审/实测后填入记录，运行完整版技能中的 [check_page_redesign.py](../scripts/check_page_redesign.py)：

```bash
python3 <技能目录>/scripts/check_page_redesign.py --project-root <项目根目录> --audit <项目根目录>/docs/page-redesign-audit.json
```

退出0只代表所提供清单、源码指纹与本地证据完整；退出1表示不完整/无效；退出2表示文件或环境无法验证。脚本只读，不联网、不打开浏览器、不修改业务数据。Python需3.9以上，无可用Python时手工逐条核对并记“脚本未运行”，不能编造通过。

**脚本会逐个核对视图文件是否登记到页面（未登记也未排除即失败），要求逐个实体给出主单/明细/独立的业务角色与依据（不按表名或外键认定，判为明细的必须并入主单工作页），反向枚举 Spring 控制器返回视图及非片段 JSP，发现未登记页面；并从页面源码反向枚举显式声明的操作键（`operationKey`、操作对象 `key`、`@PreAuthorize`/`@RequiresPermissions`、`v-permission`、`perms`），要求每个键要么拆成独立动作写进 `businessActions[].actionKeys` 并在最终轮次的 `testedActionKeys` 里逐键实测且有对应 JSON 预期/实际结果（每动作键数上限读取 conventions.actions.maxKeysPerAction），要么用 `displacedActions` 给出可核对的承接页/替代键/未绑定源码依据，否则直接失败；被页面 import 的组件与接口封装一并参与枚举。判为明细的实体还会被扫描后端写端点：前端入口拆掉、后端 `save`/`delete` 仍对管理侧开放的，属于双轨，必须删除端点或在 `keptWriteEndpoints` 里指出对应端点方法中的父级归属校验或真实服务调用代码；POST 的名称不能作为只读豁免依据。同时拒绝明写“需人工核对”却标通过的交互证据。** 页面怎么拆由业务判断，脚本不管；但页面上有的操作一个都不能漏。 其他框架的路由、动态菜单、布局美观和证据真伪仍需实际核对；脚本不能证明真实操作发生。不能只把新哈希写回旧记录来消除失败，代码/共享依赖变更应先做受影响复验，再更新版本、证据与摘要。

交付每页决策、实际改进和复验记录；汇报“清单页数/已实现/业务复审通过/实测通过/返工/阻塞或未测”，分类口径清楚，不能把结构检查数冒充UI实测数。

## 6. 画面与统一演示口令的最终证据

按 [runtime-review.md](runtime-review.md) 交付 `docs/runtime-review.json`。先截图并实际查看，再写具体的布局／层级／控件／反馈评估；不接受仅“美观、通过”或只有尺寸数字的结论。此证据与业务审计并行成立，不能相互替代。

页面实施、检查、问题、返工与续跑由上述唯一脚本维护；页面审计继续作为真实验收证据来源。完成全部实施后集中验证，失败回原页面检查修复；冻结前生成page-task-results并完成与审计页面的双向覆盖核对。
