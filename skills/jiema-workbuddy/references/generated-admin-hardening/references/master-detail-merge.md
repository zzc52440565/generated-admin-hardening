# 主从单据归并

一表一菜单不一定符合业务。先从真实操作流程判断，不依表名的 `_detail/_item`、金额字段或外键直接合并。

## 判定

同时核对：子记录能否独立存在、用户是否独立创建/操作它、主单失效后是否仍有独立业务生命周期；再检查独立高频场景是否会因归并消失。订单行通常是组成部分；SKU、库存流水、审计记录常有独立职责。证据不足保持原结构，列出待决问题。

## 需要一起修改的链路

1. UI 为单据表头与明细编辑，保留必要的跨单查询/报表入口。
2. 输入 DTO 明确新增/编辑/移除语义。更新前校验主单与全部明细的归属、授权和合法状态，拒绝把其他主单明细 ID 塞进来。
3. 表头与明细 diff 在同一事务；总额使用十进制定点数在服务器重算。已有并发版本/行锁机制继续使用，避免丢失更新。
4. 已审核/已出库等状态按真实规则锁定；不默认添加反审核。作废、软删除、保留历史和级联行为沿用业务约定，不盲目物理删除。
5. 迁移菜单、路由、调用方、权限项、导出及测试。旧 URL 使用项目已有路由策略；不固定要求 SPA 返回 301。旧权限清理先核对引用和迁移范围。
6. 不默认改变表结构；若授权范围需要 schema 变更，按仓库迁移方式交付，不直接改生产数据。

## 验证

新增多行、修改/移除/重排、非法跨单明细 ID、已锁定状态、事务失败回滚、并发更新、重复提交、金额边界、导出包含明细、历史记录与孤儿检测。图表同步 UI 归并事实与实际类关系，不能画成数据库表已合并。

审计记录按 [记录格式](page-redesign-audit-format.md) 显式填写 `masterDetailGroups[].workspaceFiles/childViewFiles`，核对页面源码与静态引用闭包；不通过文件名包含表名判断归并。业务上是否主从、引用的组件是否实际参与用户流程以及同事务保存，仍需真实业务操作复核。

隔离实测除审计声明外，保留绑定最终版本与后端摘要的 JSON 请求/响应证据，含不同的测试用户与主单所有者、主单 ID、响应码和拒绝原因。只允许使用隔离测试账号标识，不保存令牌；真实性须由可信测试运行或独立复测确认，不能以手填状态码证明授权安全。
