# 七图统一教学案例与 ER 核对示例

这些文件是**假设业务的教学输入**，仅用于理解格式、分支和一致性；不是校园项目的修复正文，也不是任何目标项目的源码或运行证据。不能换个系统名字就提交。必须先按[事实审核合同](../../references/diagram-facts-contract.md)提取目标design/source事实，再重新写七份全文。正文只有原生语法，解释与来源记录放在项目外的事实报告。

## 本例的明确前提

范围仅为订单受理，没有支付、库存、审批、退款、履约或注册。账号已初始化，具有客户/管理员角色；访客是未登录状态，不是新建的后台角色。账号只有唯一用户名、应用编码器生成的密码哈希与角色，登录成功后会话绑定可信身份。登录失败不创建会话；客户端传入的客户 ID 不能决定数据范围。

实体为 Account、Order、OrderItem。Order 持有客户关联；明细只属于一张订单、不能脱离订单存活，故 Order → OrderItem 可用组合。没有实体行为方法，业务在服务层完成，类图不凭空添加 submit()。订单只有 SUBMITTED 状态；本例不画不存在的审批状态机。

提交：只允许已登录客户，非空商品明细，数量 1–99，请求号必填。服务先查 `(customerId, requestNonce)`；内容一致复用原结果，内容不同拒绝。唯一约束处理并发重复提交；订单与明细写入同一事务，异常全部回滚。唯一键竞争后读取原请求核对，其他数据库错误返回可恢复失败。时序详细图为可读性将事务 SQL 合并在服务与数据库之间；架构图保留实际数据访问层，这是一种明确的展示抽象，不表示绕过 Repository。

客户查询强制从会话取 customerId；管理员查询有独立管理员鉴权。两者都有过滤、稳定排序、分页、空态和拒绝分支。只读查询无写事务；不会改变订单状态。技术部署仅浏览器、HTTP入口、应用服务、数据访问层、MySQL，示例会话为服务签发的令牌；没有 Redis/队列/消息通知。

以上仅是教学前提，source只有找到相应代码/配置/结构证据才可采用；design须从需求/SQL推导并在事实报告标明方案来源，不能直接继承本例假设。缺少幂等、事务或隔离时记录真实缺口，不能把本例保护措施画成已有实现。

DFD 1.0 覆盖 login，2.0 覆盖 submit，3.0 覆盖 mine/admin-query；不要求业务场景与加工一一对应。D2 聚合两张物理表为逻辑存储，不代表改了数据库结构。并发竞争的回查经过 2.1，保持与父层相同的输入输出边界。DFD 描述数据依赖，不代替流程图的事务控制顺序。

ER 示例 JSON 是**记录格式示例**，`status: unverified` 且 `exampleOnly: true`；设计版本和数量是假设值。真实记录须由 diagram_status/project_show 回执填写，不直接提交本文件。除 PK/FK、可空性、基数外，必须按[ER 关系审查](../../references/diagram-facts-contract.md#er-关系审查)逐条核对 name、业务阅读方向、状态条件与事实依据；技术 ID 不等于显示名。与design业务/SQL依据或source实际数据库/ORM对照，有差异保留并阻止宣称结构一致，不偷偷重建或改项目。

## 身份与事实先于格式

1. 读取目标项目当前 ProjectDesign、revision、来源指纹与现有全文；记录保留/新增/删除和差异。
2. 用 `diagram-facts-contract.md` 逐行关联所选design/source事实，核查核心场景的授权、成功、失败、事务、并发。
3. 完整替换会删除未列项；同名的两个规范操作可能代表不同权限，禁止按名称合并。语义不变应为零命令，修改存在歧义则保留草稿并定位身份，不反复换词试保存。
4. 用正式解析器/diagram_apply回包核对成员数和内容；解析成功只证明输入合法。保存及原生页面显示仍单独验证，用例保存后再回读功能结构。

随包 `.txt` 是唯一教学正文；分图指南只引用，避免出现不同版本。仓库回归测试直接读这七个文件，检查解析、分支/消息保留、往返、跨层边界与坏节拒绝。测试夹具通过不代表目标项目通过。
