# 建项前业务决策与用户选择

先完成**有明确默认分支、权限完整且生命周期闭环**的不收费设计预演，再把真正影响实体、关系、公开范围、敏感授权或核心流程的选择一次列给用户。WorkBuddy 应承担日常设计取舍，不把“原文没写经办人”直接变成矩阵空格；普通基础资料和账号维护可由已有 Admin 或相容管理身份按最小权限承接，并标记为模型建议。推荐不是用户原话；只读预演不调用建项、生成、图稿保存或计费工具。已经由用户资料明确回答的问题不要重复提问；只影响下载后实现细节的事项写入开发清单。

**只问模型无法安全默认的关键业务选择。** 功能被要求但原文未说谁办理时，先在推荐矩阵里由已有 Admin 或相容业务管理身份承担，并说明为什么该分工最少角色、最少权限；无需为每张表另起一个 Qn。原文已明确的禁止修改、仅本人/仅任课教师等约束直接执行，不列相反的普通选项。原文未要求的真实或模拟支付、额外岗位、成绩解锁、物理删除等扩展，标记“未纳入当前需求”，不为它们增加 Qn。原文明确要求业务“删除”但未说物理方式时，默认对有引用的记录软删并保留历史、对无历史的临时记录按需求删除；可把物理删除列为调整选项，但它不是闭环阻塞。

原文未要求的取消、退款、票据作废、报价修改、撤回、分次成交等例外流程，不能无条件加进基础矩阵。若推荐方案**自行选择**在支付、确认或完成前预占库存、余座或余额，取消/超时释放就是该方案必要的反向状态边：要么把触发者、超时任务、状态和资源回补设计完整，要么改为可信完成事件时扣减；不能一边预占，一边把释放当作可选扩展。其他例外若确为原文目标的必要前提，列出原文链条和无此操作的具体断点；否则放在可选扩展，不给推荐 grant，不升级成关键待定问题。原文未要求物理删除时连“非阻塞选择题”也不用列，直接说明本轮拒绝物理删除即可。

角色清单和数量均未固定时，默认从不超过三个身份中安排一个 `Admin`，实际承担账号、主数据和参数的必要管理；若用户已指定三种独立身份，则在兼容职责的既有身份内安排管理，不能再虚增第四人。这个默认与基础生成器的需求分析原则保持一致，仍须逐表列明 Admin 实际需要的权限。

某个报表按代售地、部门或网点汇总，不等于该地点或组织有独立登录人员；原文没有明确独立身份时，不能把统计维度当成突破三角色上限的理由。所需数据可由既有授权岗位受控导入，或由具名集成任务采集；若两者都无安全可行来源，就如实写设计断路，不通过添加无依据角色掩盖。

**预演矩阵必须完整，但要注明它是推荐分支。** 每个角色 × 实体 × 四动作都有允许或拒绝；模型建议的允许格标“建议”，原文明示格标“明”，必然推导格标“必推”，并说明记录范围和字段。若用户改选，重算受影响格；不能把不同分支的权限取并集。管理员可按推荐职责开通非自助账号、维护基础资料，但维护机场不自动带来读取全部旅客资料或订单的权限。账号启动要设计自注册、Admin 开通或具名部署导入中的一种具体路径，不能只写“总得有人开通”。真正的 `AUTHORITATIVE` 提交矩阵只采用已确定的同一分支。

**推荐格与替代分支分开写。** 例如矩阵写“建议·按 Q2A：管理员维护商品”，Q2B 若改由业主维护，就在问题区说明这两列如何换，不能把 Q2B 的 grant 也写入同一矩阵。某个实体的普通编辑与发布/取消是不同业务用途，状态字段只由受控操作赋值。原文只说“维护/管理”不能推导物理 `DELETE`；可在推荐方案中使用停用、作废等受控 `UPDATE`，但无依据的物理删除始终拒绝。

原文明确写“删除”时，先区分业务上移除可见记录与数据库物理 `DELETE`。推荐软删时，相关实体的 `UPDATE(status)` 是受控建议权限，`DELETE` 为拒绝；若用户明确选择物理删，再核对外键和历史约束，重算**所有受影响实体**。问题影响清单必须和矩阵、生命周期账本逐项对应，不能在一张表写软删，另一张表偷开物理删除。

每项关键选择还要指出它影响 [生命周期账本](structure-and-permissions.md) 第 4 节的哪一行、哪一步。账号开通者、首条业务记录来源、订单明细的父流程、状态终点和读取范围都应在推荐分支给出具体设计；不能以“系统自动”或未来开发代替当前设计路径。默认登录角色最多 3 个；原文没有第 4 个独立操作身份依据时，不把“再设系级教务/财务/平台管理员”作为普通方案。用户主动补充新角色需求后，才重新评估角色上限。

“查看本人订单”能证明旅客需要登录，**不能单独证明旅客必须开放匿名自助注册**。推荐方案应根据整体场景选一种具体的账号取得方式并标明推导，例如面向公众的购票可建议受控自助注册，内部员工可建议由 Admin 开通；模型不能同时开放两种入口而不说明原因。平台默认 `Admin` 演示账号是独立种子政策，不等于其他业务账号也有默认开户来源；非 Admin 账号须由推荐矩阵中的开通者或具名导入产生。

## 每一项都给出可选答案

**先说用户会看到什么，再决定怎样实现。** 面向普通用户的问题和选项不用“软删除、级联删除、RBAC、中间表、外键、CRUD、SELF/RELATED/ALL”等实现词。只问选择后系统行为真的不同的事项；模型自己处理纯技术实现。首轮最多提出 1–3 个最关键的问题；宿主原生 `AskUserQuestion` 一次最多呈现 4 题，其余在用户点选后按依赖继续，不一次抛十几题。若某问题只改变下载后的实现方法而不改变用户体验、数据或权限，直接记入开发清单，不制造选择。WorkBuddy 5.9.3 真机已验证原生选择卡可用：每题 2–4 个互斥选项，并自带“其他补充”自由输入。**必须调用这个控件**；Markdown 表格、聊天 A/B 回复和另起“是否补充”题均不能代替。关键影响在题目或选项的一句话后果中说清，技术细节留在设计说明。

例如不要问“是否开启软删除”，应问“管理员停用一个用户后，他以前发的帖子怎么办？A（推荐）保留帖子并显示‘账号已注销’；B 同时隐藏帖子；也可以写你的处理方式”。推荐项附一句依据，并说明哪类页面或历史记录会变化。用户选择“按推荐”只能应用已展示的普通推荐；资金、敏感授权和与原文冲突的职责仍须记录用户明确答复，不能由模型代填 `USER`。

使用稳定编号，逐条写全以下内容，不只列一句问号：

1. **待定问题**：说明当前已知事实和还缺的决定，不把模型推测称作“需求明示”。
2. **推荐选项**：明确标 `推荐 A/B/…`，给一条基于当前需求、最小权限和交付成本的理由。推荐只能帮助选择，不能自动提交。
3. **其他可选项**：至少一个与推荐互斥的方案。选项描述应让非技术用户看懂，不用 `SELF/RELATED/ALL` 代替业务语言；自定义要求使用控件每题内置的“其他补充”，不占一个预设选项。
4. **设计影响**：分别点明会变化的实体/关系、页面或登录入口、可见或可修改的数据范围，以及生成器可做和下载后仍需开发的部分。若影响收费或外部凭据，明示需另行确认。
5. **补充说明**：每题允许在内置“其他补充”输入适用角色、业务例外、上线阶段或已有数据库限制；不要新增一题询问是否补充，也不要要求用户手打字母。

选项必须处于已选平台和实时合同可支持的设计范围内，而且每个选项都要保持最低安全边界：付款状态、实收金额、库存、里程和业务终态只能由可信服务端流程赋值，不能把“用户自己标记已付款”列成可选实现。模拟支付也需要受控的服务端测试流程，并明确它不证明真实收款。用户自由补充的需求若超出生成器能力，说明具体缺口与下载后开发路径；若超出所选技术栈，给出支持的选择，不静默改栈或把暂不支持包装成已交付。

**把每个选项当成独立方案做反向攻击。**自助注册不得凭证号、手机号或姓名认领已有账号、档案和历史业务；若只新建身份，要明确新账号只能看到自己的新记录，如何核验、激活、处理重复档案，以及核验前能做什么。固定借期、价格、配额等规则不能一边称“全员统一”，一边允许经办人任意改结果；例外须单独列为受限操作，写清范围、原因、审计和对应权限格。逐项检查“选项描述 → 字段可写/服务端赋值 → 权限与状态边 → 用户看到的结果”，任何一处冲突先改方案，不把不安全或自相矛盾的备选交给用户决定。

在同一 WorkBuddy 任务中把真正关键的待定问题交给原生选择控件。推荐矩阵明确采用哪套默认设计，同时注明哪些来自模型；不能声称用户已选择。用户跳过或在其他说明里写“暂不确定”时，若该项涉及敏感授权、资金或与原文冲突的职责，检查点标 `awaiting_user` 并保留原任务；其它普通默认设计可继续作为候选供审查，不把模型建议改写成用户原话。收到选项后自动接续，不要求再发“继续”。

输出前逐项对照“问题编号 → 当前推荐分支 → 其他选项 → 受影响的全部实体和 CRUD 格 → 推荐矩阵标记 → 生命周期账本 → 页面/关系分支”。同一选项编号在正文、预演稿和关系路径账本中必须始终指向同一个方案。例如 `Q7A=员工不看订单` 时，推荐矩阵不能又写“员工订单 RELATED 仅 Q7A”；允许本航司订单读取的路径只能归属于相应的开放选项。发现编号或权限冲突先修正整份预演，不能交给用户自行猜哪处有效。

## 选择后的闭环

- 逐项记录“问题编号 → 推荐 → 用户选择/补充原文 → 最终业务决定 → 受影响的结构、权限和页面”。用户自定义答案与预设不一致时，优先理解其真实意图；必要时只追问冲突的那一项。
- 按最终选择重新设计实体、外键、登录身份、`AUTHORITATIVE` 权限矩阵、逐操作前提和逐实体生命周期账本；重新审查角色数、所有 `ALL` 与每个必需实体的来源和可达路径。不得保留与选择冲突的旧草稿、关系路径或图稿。把“用户明确”“模型推导”“用户选择后确认”“仍未确认”分开标注；推断不能写成“明文依据”。
- 每一项允许的新增权限必须能追溯到用户原话、原文必然推导、模型明确建议并纳入同一推荐分支，或用户本轮选择。用户改选后完整矩阵逐角色、逐实体、逐动作重算；账号开通、旅客资料读取和跨机构订单读取都单独检查，绝不把不同分支合并。
- 回答齐全后只需简短回显关键决定并继续原任务，不再为同一选择重复征求确认。真实捷码积分报价、设备授权和危险操作仍按各自独立确认流程处理。

例如航空售票场景中，“航班是否允许未登录浏览”“员工能否看本航司订单”“支付是实接还是模拟”“谁维护航司资料”“能否代他人买票”“是否区分舱位”分别改变公开页面、隐私权限、凭据依赖、维护角色、乘机人关系和库存/价格结构。若模型提出这些问题，就逐条给推荐、互斥选项和上述影响，再由用户选择；不能只在末尾罗列六个问句，也不能先建项再让用户补答案。
