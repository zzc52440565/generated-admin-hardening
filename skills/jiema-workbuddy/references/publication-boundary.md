# WorkBuddy 运行与发布边界

本页只写**有公开出处的事实**和由此推出的边界。未查到的能力按「未验证」处理，不用本机经验代替平台结论。

## 1. 官方事实

| 事实 | 出处 | 对本技能的约束 |
| --- | --- | --- |
| 技能包结构为 `SKILL.md` + 可选 `references/`、`scripts/`、`templates/`；`scripts/` 里的脚本「由 AI 通过 Bash 工具执行」 | 开放平台《技能》 | 技能可以携带本机脚本，但执行者是宿主，不是技能自身 |
| 技能市场 ZIP 的 frontmatter 必填 `name`、`display_name`、`display_name_en`、`description`、`description_zh`、`description_en`、`version`、`author`；提交 ZIP 会经过安全检测 | 开放平台《技能》 | 随包技能必须补齐这些字段；扫描不通过就不能上架 |
| 连接器（MCP + Skill）一个连接器只能一个 MCP Server；`mcp.json` 的 stdio 可声明 `runtime` 由 WorkBuddy 托管 Node，`npmRegistry` 可配镜像 | 开放平台《连接器》 | MCP 包的可用性取决于 npm 包是否真的可安装 |
| 默认权限以**工作空间**为边界：工作空间内常规文件操作通常直接执行，越界或高风险操作暂停请求确认；需确认的类型包括「执行脚本、命令或外部程序」「写入受保护或敏感路径」「删除受保护文件/批量删除」「网络访问」 | WorkBuddy《默认权限与安全沙箱》 | 每个安装/修复命令都可能被用户拒绝，技能必须能停下来并把选择权交回用户 |
| 「允许完全访问」是**全局开关**，关闭二次确认，可执行命令、安装软件、改系统设置；官方明确建议只在隔离、可恢复任务中短时开启，并列出「工作目录靠近桌面/下载目录/仓库根目录」「需要运行不了解的脚本」等不建议场景 | 同上 | 不得把「请先开启完全访问」写成前置条件或默认建议 |
| 安全中心可细化：文件按路径三态（允许/询问/拒绝）、命令按前缀、网络按域名、工具与 MCP 管控、敏感保护（默认开启，输出侧会拦截凭证外泄）、删除保护与批量删除审批、审计中心；macOS 另有完全磁盘访问/辅助功能/自动化授权 | 同上 | 敏感保护会拦截把口令写进输出；脚本必须默认脱敏；审计可查，不能宣称「私下执行」 |
| 网络：远程 HTTP 请求默认询问、本地 HTTP 默认放行；macOS「网络严格模式」会影响 SSH、直连数据库工具 | 同上 | 本机数据库/端口检查要容忍被网络策略影响，并给出关闭严格模式的说明而不是静默失败 |
| 含 `.codebuddy` 等开发配置目录的工作区首次打开要选择信任，受限模式不加载、不运行工作区内的设置与脚本 | 同上 | 项目目录里的脚本不能假设会被自动执行；安装/修复动作不依赖项目内脚本 |
| 客户端提供 Windows、macOS（以及 UOS、麒麟）安装形态 | WorkBuddy 文档导航 | 双平台都要有实现，但平台结论必须分开取证 |
| Agent 可自动操作内置浏览器，右侧实时展示页面；支持读取URL/DOM和截图。首次使用在“设置 → 智能体 → 浏览器操控”安装组件；点击对话链接也可打开内置浏览器 | [WorkBuddy《右侧边栏》](https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Right-Sidebar) | 授权、在线编辑和Web预览默认由宿主自动打开；组件缺失/权限拒绝如实记录，不能把备用链接或独立浏览器当自动展示通过 |

## 2. 由此确定的边界

1. **技能能带脚本，但不能保证脚本被执行。** 执行权在宿主与用户手里：命令被拒绝、被沙箱拦截、被网络策略挡住都是正常结果。任何阶段都必须能「停下来 + 说明 + 保留检查点」，不能因为一次被拒就把流程写成失败。
2. **文件访问以工作空间为界。** 默认权限下写工作空间外、写受保护路径都要确认。MCP 侧还有自己的允许根目录（`JIEMA_WORKBUDDY_ALLOWED_ROOTS`，默认 `~/WorkBuddy`）。下载目录、检查点、日志都应落在工作空间或用户主目录下的专用目录，并提前告知用户位置。
3. **没有提权通道。** 需要管理员权限的动作只能「向用户展示要做什么 → 用户确认 → 宿主执行」。因此环境阶段的**首选方案必须是不需要提权的用户级安装**（用户级前缀、官方压缩包解压到用户目录、项目内包装器），系统级安装（全局包管理器、注册服务、改系统 PATH）只能作为明确标注影响的备选。
4. **敏感保护默认开启。** 口令、令牌出现在命令参数或输出里会被拦截。所以：口令只经安全输入或配置文件传递，日志与报告一律脱敏，MySQL 本机开发实例的约定口令只在计划里以「约定值」形式向用户明示，不回显真实凭据值。
5. **双平台分别取证。** macOS 上验证过的安装动作不等于 Windows 可用；Windows 脚本在 macOS 只能做静态检查。发布文案与技能正文都必须区分「已在哪个平台实测」。
6. **安装确认发生在宿主层，不在技能内部。** 技能能做的是：把动作、路径、影响、回滚、复验提前列清；不能自己做二次确认，也不能替用户勾选「完全访问」。
7. **发布后的能力仍受宿主约束。** 市场安装成功只代表技能被加载，不代表本机脚本可执行、不代表能安装软件、不代表 macOS 与 Windows 都通过。
8. **右侧网页导航由WorkBuddy宿主执行。** 捷码MCP返回URL后，模型还须调用当前宿主的内置浏览器能力，流程见 [浏览器交接](browser-handoff.md)。不要求捷码服务端控制浏览器，不猜测固定工具名称；网页Cookie按WorkBuddy账号隔离，不能代替MCP认证回读。

## 3. 能力分级（写文案时的唯一口径）

| 级别 | 含义 | 可以怎么写 |
| --- | --- | --- |
| 本地已实测 | 在本机真实运行并留下输出证据 | 「已在 macOS 26.2 / node 24 上本地实测」并给出命令与结论 |
| 仅静态验证 | 只做了语法、结构、链接或文本检查 | 「已通过静态检查，未在目标平台运行」 |
| 待真机验证 | 需要 WorkBuddy 客户端、市场安装、真实账号或目标操作系统 | 「尚待真机验证」 |

禁止表述：把「本机能装」写成「技能会自动装好」；把「脚本存在」写成「已支持」；把「macOS 通过」写成「双平台通过」；把「ZIP 能下载」写成「业务完成」。

## 4. 发布前必须满足

1. 包内无本机绝对路径、无真实凭据、无被审查源包的默认批量安装/弱口令/重建数据目录/跳过校验动作。
2. 技能 frontmatter 字段齐全，Markdown 相对链接全部可解析，脚本语法可检查。
3. 连接器 `mcp.json` 指向**真实可安装**的服务器包；未发布时必须显式标注为阻塞项。
4. 交付说明同时给出三档证据：本地实测、仅静态验证、待真机验证。
