# 生成项目加固、SQL 重设计与图表同步

把生成项目中已有或用户明确要求的业务做实，重设计与业务不符的初始 SQL，让应用、数据库对象与交付图表一致。先确定项目事实与授权范围，再选择检查项；不把经验样例当成当前项目的需求。

带缺失检测、固定版本安装和当轮接续的完整任务提示见 [PROMPT.md](PROMPT.md)。若本轮刚安装，实际读取本文件及所需参考后继续用户任务；文件已安装与客户端原生发现分别说明，不以安装提示代替工作交付。

## 执行边界

- 遵循用户指令和目标仓库规则。明确是只读审查、修复实施，还是只更新图表；只读请求不修改文件、数据或启动有写入副作用的脚本。
- 默认保护已有数据、账号、schema 和用户改动。核对连接环境后使用本地隔离测试数据；不默认清库、重建种子、放宽字段、改密码、增加角色或功能。
- 用户要求 SQL 优化时，可在交付脚本中按真实需求重设计表、约束和数据库对象，并同步调用方；这不等于获得对已有库执行迁移、删表或改数据的授权。空库安装与保留数据升级分开，不能让“保护 schema”变成只改 SQL 排版。
- 修复授权覆盖范围内的缺陷并迁移调用方；不能据“业务上可能需要”自行新增支付、短信、审批、自动计费等产品能力。确有高影响歧义时提出具体问题，继续独立工作。
- 不自动提交、推送、发布或调用生产接口。安装依赖、启动服务、数据库迁移和清理遵循当前环境权限；不把技能视为额外授权。
- 复用已有测试登录方式或用户提供的会话。不得为自动化新增认证后门、记录明文验证码，或反复登录触发锁定。

## 1. 建立事实与完成定义

先读实际目录、依赖锁文件、启动脚本、路由/窗体、接口、业务服务、模型/schema 和现有测试。记录：

- 项目类型、技术栈及真实版本；主要用户、现有角色、核心业务和应用入口。
- 菜单/页面 → 操作 → 接口/方法 → 权限 → 数据模型的映射；区分真实实现、空壳和未证实能力。
- 当前改动、可运行命令、已知失败、测试数据归属；不要输出秘密或复制真实用户数据。
- 初始 SQL、后续 migration、实际数据库方言/版本、ORM/Mapper 和已有视图/过程/触发器；SQL 脚本、当前模型与数据库实态不一致时逐项记录，不能任意选一份当真。
- 任务范围、完成标准、依赖顺序和验证矩阵。非简单任务复用仓库账本；无约定时在约定输出目录记录简短计划。

运行故障复现可作为基线；不要为了“跑起来”擅自迁移数据库或覆盖运行进程。环境不足时标记未验证，继续静态分析。

## 2. 按证据选择改造

从 [audit-checklist.md](references/audit-checklist.md) 选择相关项；不同平台查 [project-type-matrix.md](references/project-type-matrix.md)。主从归并查 [master-detail-merge.md](references/master-detail-merge.md)，权限问题查 [rbac-audit-redesign.md](references/rbac-audit-redesign.md)，接口/数据契约查 [crud-rbac-gap.md](references/crud-rbac-gap.md)。需要具体实现提示时再读 [code-patterns.md](references/code-patterns.md)。

对每个缺陷保留触发条件、证据、根因、改法和预期验证。先完成同一依赖链的全部实现、调用方迁移和相关测试，再按矩阵集中验证；失败后只重跑受影响项。

提供初始 SQL 或任务涉及数据访问时，先按下一节形成数据库对象与调用契约，再收口应用改造；图表以最终接入的实现为准。

重点判据：

- 表单的关联选项、回填、边界校验和失败恢复正确；金额、权限、状态等关键值由服务端校验。
- 按钮对应真实能力，正常导航、下载、刷新、状态变化都可构成有效反馈；不能只认弹窗或提示。
- 筛选核对请求字段、后端条件、返回记录/总数与已知样本。行数未变化不能直接判错，参数变化也不能证明后端已过滤。
- 权限检查菜单、操作、行范围和字段；同时覆盖列表、单条查询、修改、导出及附件。权限矩阵以已确认业务为准。
- 布局测量可见尺寸、滚动和可操作性；允许业务需要的表格内部滚动。不强制某种登录页风格或无条件重做 UI。
- 数据和图片先检查现有资产。仅对已授权的演示数据补齐缺口，采用幂等脚本与隔离标识；图片优先复用合法素材，缺素材时说明而非编造已完成。

## 3. 初始 SQL 与数据库对象重设计

**拿到初始 SQL 后，默认完整审查并重设计 CRUD、视图、存储过程与触发器，不能只格式化、加索引或补几条示例。** 原脚本对象和业务假设都需复核，缺失对象也纳入目标设计；每类给出保留、重构、新增、移除或目标数据库不支持的结论及依据。

先读 [sql-redesign.md](references/sql-redesign.md) 建立顺序与交付，再读 [sql-object-design.md](references/sql-object-design.md) 逐类设计。接收端为本系统时读 [sql-studio-compatibility.md](references/sql-studio-compatibility.md)，验收按 [sql-validation.md](references/sql-validation.md)。交付结构见 [SQL 交付模板](assets/sql-delivery-template.md)。

- 按真实业务重定字段类型、键、关联、唯一/检查约束、索引及数据生命周期；保持用户要求的数据与兼容范围，所有名称变化有旧→新映射。
- CRUD 分别覆盖新增、读取/筛选/分页/统计、修改、删除/作废；参数绑定、权限范围、并发、主从事务和返回语义一起设计。不是给每张表机械复制四句 SQL。
- 视图明确业务查询、投影、连接基数、统计口径及授权边界；存储过程明确调用方、参数/结果、事务与错误契约；触发器明确表、事件、时机、触发条件和副作用。全部引用最终真实表与字段。
- 用户明确要求这些数据库对象时，为目标数据库支持且业务可落实的类型交付完整定义与调用/测试 SQL；不能只因已有 ORM 就整类跳过。没有业务依据、与既有职责冲突或数据库不支持时，写明原因与能满足需求的替代方案，不凑对象数量。
- 一条业务写入/计算规则只由一个 owner 执行。存储过程、触发器与应用服务不能重复扣库存、累计金额或写审计；替换时同轮迁移 Mapper/Repository、服务、接口契约与测试。
- 分开交付 Studio 结构导入 SQL、数据库部署脚本和独立测试脚本；不能承诺导入 SQL 后系统会自动保留/调用所有视图、过程与触发器。客户端 `DELIMITER`/`GO` 和程序驱动执行也分别适配。
- 验证覆盖新装、已有数据升级、对象调用、失败回滚、跨用户/租户、批量与并发。没有目标数据库实测时标为“已设计/静态核对，运行未验证”，不把 SQL 文件生成当作完成数据库部署。

## 4. 验证并确认最终实现

按实际项目运行定向测试、类型/lint、构建和受影响业务回归。Web 用现有浏览器工具；小程序和桌面用对应工具，不能以 Web 构建代替。

优先复用仓库测试。可选的 [browser-audit.md](references/browser-audit.md) 与 `scripts/browser_audit.py` 只执行明确配置的本地页面和用例，需要现有 Python Playwright；不安装依赖、不登录、不扫描并点击所有按钮。报告区分 `passed / failed / unverified`，缺工具、缺数据或未覆盖场景不能算通过。

验证完成后冻结“最终事实清单”：实际角色及权限、功能入口、类与方法、调用顺序、状态条件、数据读写、组件依赖、已部署且真实接入的视图/过程/触发器。区分“仅定义”“已部署”“应用已使用”；尚未接入的 SQL 不能画成运行中的能力。若后续代码或 SQL 变化，重新核对受影响证据和图表。

## 5. 根据最终代码与 SQL 同步七类图

完成代码改造后，默认交付功能结构图、领域类图、时序图、系统流程图、数据流图、架构图、用例图的更新资料。用户限定只更新部分图时遵循其范围。**此处的“系统格式”指接收图表的 Studio；图中的业务内容来自用户被改造的项目，不能把 Studio 自身架构画进用户项目。**

执行前读取 [diagram-workflow.md](references/diagram-workflow.md)，再按图种读取以下格式。格式以 2026-11-03 的真实解析器核对，版本指纹在 [studio-format-sources.json](references/studio-format-sources.json)。用户提供的当前图文本/解析器优先于旧示例；不能访问接收端时说明版本适配尚未实测。

| 图种 | 格式参考 | 当前接收方式 |
| --- | --- | --- |
| 功能结构图 | [功能结构](references/diagram-function-structure.md) | 五级缩进树，在当前图中重建 |
| 类图 | [领域类图](references/diagram-uml-class.md) | 中文命令，按完整文本更新当前领域类图 |
| 时序图 | [时序](references/diagram-sequence.md) | 参与者/消息/片段，在当前图中重建 |
| 系统流程图 | [流程](references/diagram-flowchart.md) | 整族标题、各流程分节、编号步骤与连接；一次更新全部流程成员 |
| 数据流图 | [DFD](references/diagram-data-flow.md) | 顶层/一层/多张二层合为一份整族正文，一次校验应用并保存 |
| 架构图 | [架构](references/diagram-architecture.md) | 编号节点/JSON名称/显式连接，更新当前成员 |
| 用例图 | [用例](references/diagram-use-case.md) | 参与者与三级用例树，全文更新完整图族 |

**系统流程图和DFD默认以完整图族为生成与交付单位。** 系统流程图一次覆盖真实登录与全部核心业务；DFD一次包含顶层、一层及全部需要展开的二层图，明确每张二层图的一层父加工。分别输出一份连续批量正文，让用户在网页“整族快速填写”中一次粘贴、一次“应用并保存全部图”。不能只挑一个缴费/订单流程，不能把多份单图文件当成需要用户逐张操作的默认交付。仅用户明确限定当前单图时，才按单图范围输出。

先建立“核心业务 → 源码入口/服务 → 流程成员 → DFD加工/二层成员”的覆盖清单，再生成。数量来自项目事实；所有核心业务都需有覆盖去向，原子处理不强凑二层，必须说明无需展开的依据。任何超限或资料不足都明确标记，不能静默删减业务来宣称一次生成完成。

每个图的交付由四部分组成：适用项目/图纸、单独的原生文本、代码证据、应用与移除旧项说明。文字说明不混入粘贴正文。系统流程和DFD的“适用图纸”是完整图族，批量正文以专用图族标题开头，不带外层Markdown围栏。输出建议：

```text
docs/diagram-update/
  README.md                    # 每个文件对应哪张图、如何应用
  evidence.md                  # 图元素 → 文件:行号/符号 → 验证状态
  01-function-structure.txt
  02-uml-class.txt
  03-sequence-<场景>.txt
  04-system-flowchart-family.txt # 登录及所有核心业务，一份连续正文
  05-data-flow-family.txt       # 顶层、一层、所需全部二层，一份连续正文
  06-architecture.txt
  07-use-case.txt
```

只输出有证据的元素。事实不足时对应图状态写“依据不足”，指出需要的文件或链路；不得为凑齐七图编造角色、方法、数据流、服务或技术组件。`assets/quick-fill-examples/` 仅演示语法，不能当成当前项目事实。

## 6. 交付与停止条件

交付修复说明、真实验证结果、未覆盖项、SQL 目标脚本/对象契约/迁移恢复说明、图表文件和复制指引。用户只要求部分能力时按其范围交付；SQL 不适用的类别也给出明确结论，不静默省略。图表不得声称自动修改了 Studio 项目；用户负责手动应用。类图、用例图和架构图均按完整文本更新，未包含的对应元素会移除；用例图必须交付全角色的完整图族文本，不能只贴某个角色片段。保留项的高级属性和有效高级关系按产品规则保留。

当授权范围内缺陷修复、SQL 重设计与调用迁移完成、相关验证有结果、七图资料已按范围交付后收口。列明仍阻塞或未验证的事项；不以“无限循环到所有功能合理”为停止条件。清理仅限本轮登记、独占、已无人使用的临时产物，保留交付与失败证据。
