# CRUD、视图、存储过程与触发器设计口径

每个对象需要业务目的、依据、输入/输出、作用域、前置条件、执行身份、事务/错误行为、依赖、调用方和测试。命名使用项目约定，保留真实 schema 和大小写，不凭表名猜业务。

## 表结构与基础不变量

- 按真实存储选择主键/复合键、外键与动作、业务唯一键、NOT NULL/CHECK、默认值。明确软删记录是否参与唯一性、历史数据保留和归档，不能随意级联删除。
- 金额采用项目及数据库支持的精确类型；单位、精度、舍入一致。时间明确时区和精度；状态来自真实枚举/流程。约束可表达的规则优先约束，避免同义触发器无意义重复。
- 索引由实际过滤、连接、排序、唯一性和执行计划决定；不为每列建索引，不仅凭字段叫 `status` 就建立单列索引。
- 新增/移除/重命名字段同时处理历史值、默认回填、ORM、表单/接口及类型映射；迁移不可恢复时明确，不能编造“反向 DDL 一定可回滚”。

## 新增 CREATE / INSERT

列清单显式，区分用户可写、数据库默认、服务器生成和受控字段。使用驱动绑定参数，身份/租户来自可信授权上下文；不接受客户端自报身份作为授权凭据。

主单和明细在同一事务，校验所有关联归属；金额/状态由真实 owner 计算。返回真实主键/版本/结果，处理唯一冲突、空值、非法外键。重试会重复产生单据或外部副作用时按现有业务定义幂等，不为所有表机械加新幂等字段。

## 查询 READ / SELECT

详情、列表、搜索、分页、统计、导出使用一致数据范围；列投影排除密码、令牌及无关敏感信息。排序字段白名单和唯一兜底，明确分页/总数一致性、空条件与合法空结果。

按用户场景重设计单表、条件、分组、排序、子查询和多表连接查询；选择合适方式而非每张表演示全部语法。核对一对多连接导致的主单重复和金额倍增，注意 LEFT JOIN 条件位置、NULL、重复/并列排序、软删及时间边界。业务汇总按正确粒度先聚合或使用 `EXISTS`，不靠无依据的 `DISTINCT` 掩盖错误。

查询契约写清参数名、类型、来源、可空/默认、返回列与业务含义、排序/分页和预期样本。`?`、`$1`、命名参数、`@变量` 属于不同驱动/执行方式；带占位符的代码片段标为绑定模板，不能宣称能在所有 SQL 客户端直接粘贴执行。

## 修改 UPDATE

显式更新白名单；WHERE 同时表达真实定位、数据授权、允许状态及所需版本条件。区分字段未提供与清空为 NULL，不允许借普通编辑改 owner、租户、累计金额或终态。

采用项目真实并发策略：乐观版本/条件写入、必要锁及一致锁顺序，不能“先查再无条件更新”。明细 ID 归属校验、汇总重算与审计归属同一事务。明确影响行数=0 的不存在/无权/冲突处理，影响行数>预期必须失败，不能返回假成功。

## 删除 DELETE / 作废

区分草稿删除、软删、业务作废、归档和物理清理。已结算/已审核等历史记录按真实规则保护；不默认所有表物理删除，也不无条件追加一套软删除字段。

WHERE 和批量集合必须绑定权限/租户/状态；空 ID 集合不能退化为全表删除。连同子记录、外键、附件、汇总和恢复路径核对。提供合法、非法、跨范围和关联限制用例；清理动作限定隔离样本，不能“测试后全表 DELETE”。

## 视图 VIEW

- 为业务查询/报表定义投影、连接、粒度、去重、过滤和业务口径，不是机械 `SELECT *` 或每表复制一个视图。
- 显式列名，核对字段冲突、类型、NULL、可选关联和聚合；分页排序由调用查询控制，不依赖视图中的隐含顺序。
- 解释执行身份、权限传播及租户范围。普通视图不天然构成行级授权；不要把可伪造会话变量/客户端传参当安全边界。敏感字段不能因 join 又泄漏回来。
- 明确普通/物化视图区别，只有目标引擎支持且有刷新/一致性需要时才设计物化方案。调用方读取视图时同步结果映射与索引/计划验收。

## 存储过程 PROCEDURE

- 以真实业务操作/复杂查询为单位设计，列出 IN/OUT、参数类型/顺序、NULL/默认、结果集/返回码和调用示例；不复制空壳过程或所有表机械包装 CRUD。
- 明确事务由调用者还是过程拥有。过程不能无意提交调用方事务；异常/约束失败应回滚适当范围并传播稳定错误，不能吞错后返回成功。考虑嵌套事务/保存点和目标数据库真实行为。
- 复核幂等、锁顺序、并发更新、死锁后的整笔重试范围、影响行数和批量规模。动态 SQL 只在必要时使用且值绑定、标识符白名单。
- 执行权限最小化；移除导出脚本里的个人 `DEFINER`/超级用户假设，按目标数据库审查 definer/invoker 或等效安全上下文。
- 项目采用过程时，迁移到唯一的调用路径，并移除重复应用写入；仅作教学时说明未接入应用。

## 触发器 TRIGGER

- 明确所属表、INSERT/UPDATE/DELETE、BEFORE/AFTER/INSTEAD OF、行级/语句级、真实触发条件及 `OLD/NEW` 或 `inserted/deleted` 差异。只监听相关字段，值未改变时避免重复副作用。
- 优先用于真实需要数据库自动保障的跨入口不变量/必要审计。外部通知、HTTP、邮件、支付和长事务不放在触发器；需要异步交付时沿用真实已有机制，不能凭空增加消息系统。
- 不与应用/过程重复扣减、累计或写审计；核对递归、互相触发、级联动作、顺序依赖、批量多行、失败回滚和性能。数据库连接用户不一定是业务操作者，不伪造可信用户身份。
- 针对 SQL Server 等语句级触发器采用集合逻辑，不把 `inserted` 当只有一行；针对 MySQL 等引擎核对同表修改及事务限制；PostgreSQL 等的触发器函数与绑定分别部署。以目标版本官方规则为准。
- 提供真实的触发动作、触发前后断言、合法不触发路径、批量与失败回滚测试。数据库内副作用是否回滚要按引擎/对象确认，不能假定外部副作用会自动回滚。

## 防止重复责任的示例

如果真实订单服务已经在一个事务里累计总额，新增触发器又执行同样累计就会重复。必须选择并验证唯一 owner：或由服务/过程统一计算，触发器只保护其他真实不变量；或让触发器接管并迁移所有写入口。不能为了“有触发器”添加第二次累计。该示例不代表任何当前用户系统必然存在订单或总额字段。
